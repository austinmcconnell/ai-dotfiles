# Claude Code Configuration

Permission rules and hooks for Claude Code (the `claude` CLI). Configuration is symlinked to
`~/.claude/settings.json` by `install/claude-code.sh`. Steering and skills are managed separately by
`install/ai-tools.sh`. Claude Code uses a simpler configuration model than kiro-cli — no agent JSON,
and global hooks live in one `settings.json` event array rather than kiro's per-agent hook blocks.
Claude Code does support custom subagents (personas) via markdown files with YAML frontmatter — a
different mechanism from kiro-cli's JSON agent configs, but the same underlying idea, including
their own scoped `hooks:` field for persona-specific hooks; see Personas below.

## Philosophy

- **Parity with other tools**: Deny lists mirror Kiro CLI and Cursor — same commands blocked, same
  files protected, same system paths restricted
- **Deny-first security**: Deny rules always win regardless of allow rules. Sensitive files blocked
  at multiple levels (permission rules + hooks)
- **Minimal friction for reads**: Allow all file reads without prompting; deny rules block sensitive
  files (`.env`, `.key`, `.pem`, credentials)
- **Parity with Kiro CLI write model**: Allow edits in project directories without prompting; deny
  rules block system paths
- **Cross-tool hooks**: Shared hook scripts work identically across Kiro CLI and Claude Code

## Directory Structure

```text
etc/claude-code/
├── settings.json    # Permissions (allow/deny) and hooks configuration
└── agents/          # Persona sources (generated into ~/.claude/agents/ with steering inlined)
    ├── docs.md
    ├── jira.md
    ├── ansible.md
    └── datadog.md
```

Additional files managed elsewhere (not stored here):

- `~/.claude/CLAUDE.md` — generated by `install/ai-tools.sh`; a slim pointer file (see Steering and
  Skills below), not a concatenated dump
- `~/.claude/rules/` — generated by `install/ai-tools.sh`, one file per steering doc
- `~/.claude/skills/` — symlink to `etc/ai/skills/`
- `~/.claude.json` — MCP servers and session state, bootstrapped by `install/claude-code.sh` (not
  symlinked — contains local state)

## Configuration Model

### Permission Rules

Claude Code uses `allow`/`deny` arrays in `settings.json` with pattern matching:

- **`Bash(pattern)`** — shell command permissions (equivalent to kiro-cli's `shell.allowedCommands`)
- **`Read(pattern)`** — file read permissions
- **`Edit(pattern)`** — file write permissions (equivalent to kiro-cli's `write.allowedPaths`)

Evaluation order is **deny → ask → allow**. The first matching rule wins. Unmatched operations
prompt for user approval (equivalent to kiro-cli excluding tools from `allowedTools`). There is no
`allowedTools` concept in the global permission model — everything is allow/deny/prompt — though a
persona's `tools:` frontmatter is a coarser analog (see Personas below).

### Pattern Syntax

- `*` matches any sequence of characters including spaces
- Paths support gitignore-style patterns: `./relative`, `**/recursive`, `~/home`
- `//path` for absolute filesystem paths
- A single leading slash is NOT absolute: `/path` anchors at the settings source, so `Read(/etc/**)`
  in user settings matches `~/.claude/etc/**`, not `/etc`. System-path rules must use `//etc/**`

### Security Parity with Other Tools

The deny list mirrors protections from kiro-cli and Cursor:

- `.env` files blocked via `Read(./.env*)` and `Read(**/.env*)`
- Credential files blocked (`.key`, `.pem`, `credentials*`)
- System paths blocked for reads and writes (`/etc/`, `/usr/`, `/bin/`, `/sbin/`, `/System/`),
  anchored with `//` (see Pattern Syntax); `scripts/validate-claude-path-rules.sh` rejects the
  single-slash form at commit time
- Destructive commands blocked (`rm`, `sudo`, mutating `gh` commands, `kubectl apply/create/delete`)

### Hooks

Six global hook events configured in `settings.json` (all commands resolve via `$AI_DOTFILES_DIR` to
`etc/ai/hooks/`, the same shared scripts kiro-cli uses):

- **`SessionStart`** (`matcher: "startup|resume"`) — runs `recall-memory.sh` (surfaces engram
  memories for the current project, tagged `AI_AGENT_NAME=claude-code`) and
  `check-engram-hygiene.sh` (time-throttled nudge for pending engram conflict relations). This is
  the Claude analog of kiro's `agentSpawn` — see `etc/kiro-cli/README.md`'s Hook Patterns section
  for the shared cadence/scoping logic. A third hook, matcher `"startup"` only (not `"resume"`),
  runs `suggest-agent-fit.sh`.
- **`PreToolUse`** with `matcher: "*"` — runs `block-env-files.sh`, `block-sops-age-files.sh`,
  `block-ssh-private-keys.sh`, and `block-shell-trace-mode.sh` on every tool call, each blocking
  access to its class of sensitive file (or, for the trace-mode hook, shell `set -x` output that
  would print secrets in cleartext) by inspecting tool inputs and exiting `2` if found. A
  `matcher: "mcp__engram__.*"` hook runs `block-memory-secrets.sh` to stop credentials from being
  stored in persistent memory (see the MCP-prefix normalization note in `etc/kiro-cli/README.md`'s
  Security Layers section — the same script handles both tools' naming conventions). A
  `matcher: "Bash"` hook runs `block-persona-shell-commands.sh`, which self-scopes via the
  `agent_type` field in the hook payload (see Personas below).
- **`PostToolUse`** with `matcher: "Bash"` — runs `audit-shell-commands.sh` asynchronously
  (`async: true`) to log AWS and kubectl commands to `~/.local/share/ai-audit/command-audit.jsonl`
  (a single shared log, not split per-tool like kiro's `aws-audit.jsonl`/`kubectl-audit.jsonl`). The
  trigger timing differs from kiro's `code` agent, which wires the same script on `preToolUse` for
  `execute_bash` (audited before the command runs); Claude wires it on `PostToolUse` (audited
  after). Harmless in practice — the script only reads `.tool_input.command`, it doesn't need to act
  before execution — but worth knowing if this script ever grows a blocking responsibility.
- **`UserPromptSubmit`** — runs `correction-capture.sh` on every prompt, the capture half of the
  capture-and-promote learning system (see the `capturing-corrections` steering and the
  `distill-learnings` skill; full mechanics documented in `etc/kiro-cli/README.md`'s Hook Patterns
  section, which is cross-tool). A second hook, `suggest-context-checkpoint.sh`, nudges once per
  growth phase when the session crosses a fixed token count, so there is a visible warning before
  auto-compaction fires. Claude Code only: kiro has no local token data.
- **`PreCompact`** and **`PostCompact`** (`matcher: "*"`) — both run `log-compaction-event.sh`,
  which records each compaction to the local ai-usage store. Purely observational.
- Claude has no MCP `aws`/`kubernetes` tools to audit, so there's no equivalent to kiro's
  `use_aws`/`@kubernetes` matchers.

### Cost Controls

Spend is bounded by four settings, none of which is a spend cap (Claude Code has no persistent
session-total budget; `--max-budget-usd` is a per-invocation CLI flag only):

- **Effort pins** — `modelSettings` sets `effortLevel: "medium"` for `claude-sonnet-5` and
  `claude-opus-5`. Keys prefix-match, so they cover the 5.5 releases too. Sonnet 5 and Opus 5
  default to `high`, so the pin saves tokens there; on the 5.5 models `medium` is already the
  default, so the pin only guards against a future default increase.
- **Effort ceiling** — top-level `maxEffortLevel: "high"` stops a session from escalating to `xhigh`
  or `max`.
- **Haiku floor for delegation** — `env.CLAUDE_CODE_SUBAGENT_MODEL=haiku` runs anonymous subagents
  (no model pinned) on Haiku. It is third in the documented precedence, below a per-call `model`
  parameter and a persona's `model:` frontmatter.
- **Agent model gate** — `Agent(model:opus)`, `Agent(model:fable)`, and the `claude-opus*` /
  `claude-fable*` full-ID forms are in `permissions.ask`, so a per-call override to an expensive
  model prompts instead of silently outranking the Haiku floor. Rules match the literal value Claude
  sends, hence the separate alias and full-ID patterns. `ask` outranks the bare `Agent` allow.

**Caveat:** all four personas (`docs`, `jira`, `datadog`, `ansible`) set `model: inherit`, so they
run on the main session model and bypass the Haiku floor. Only anonymous delegations (for example
`Explore` or `general-purpose`) get Haiku.

### Steering Distribution

Steering is not configured in this directory. `install/ai-tools.sh` generates per-file rules in
`~/.claude/rules/` from shared steering sources in `etc/ai/steering/`. Files with `paths:`
frontmatter get conditional loading (only injected when Claude reads matching files). `CLAUDE.md` is
a minimal pointer file, not a concatenated dump. Only the `code`, `github`, `security`, and `shared`
steering domains are distributed this way (Claude Code has no per-persona resource scoping in the
main session, unlike kiro's per-agent `resources` arrays) — domain-specific steering (`ansible`,
`documentation`, `datadog`, `scrum`) is instead inlined into each persona at install time (see
Personas below).

### MCP Servers

Claude Code stores MCP servers in `~/.claude.json` (user scope) with a different schema than
kiro-cli or Cursor:

```json
{
  "mcpServers": {
    "server-name": {
      "type": "stdio",
      "command": "npx",
      "args": ["-y", "package-name"],
      "env": { "KEY": "${ENV_VAR}" }
    }
  }
}
```

The `type` field (`stdio`, `http`, `sse`) is required — this is the main difference from kiro-cli's
format. Environment variable interpolation uses `${VAR}` syntax (same as kiro-cli).

`install/claude-code.sh` bootstraps `engram` and `jira` into `~/.claude.json` with a `jq` merge:
missing servers are added while existing servers and session state are preserved (existing values
win on key collision). The merge is idempotent, so running the installer against an existing
`~/.claude.json` lands `engram` rather than skipping the file. `engram` is guarded on the Claude
side by the shared `block-memory-secrets.sh` PreToolUse hook.

### Personas (Subagents)

Claude Code supports custom subagents defined as markdown files with YAML frontmatter in
`etc/claude-code/agents/` (generated into `~/.claude/agents/` by `install/claude-code.sh`, invoked
via `claude --agent <name>`). Four personas mirror their kiro-cli counterparts: `docs`, `jira`,
`datadog`, `ansible`. There is no persona equivalent of kiro's `code` agent — the main Claude Code
session fills that role directly.

- `tools:` frontmatter is the closest Claude analog to kiro's `allowedTools` — it gates which tools
  are *available* to the persona at all, not just whether they auto-run without a prompt
- `disallowedTools:` blocks specific tools within an otherwise-available category (e.g. jira's
  `mcp__jira__jira_delete`), mirroring kiro's MCP `disabledTools`
- `mcpServers:` scopes which MCP servers a persona can see (jira restricts to `jira`)
- Domain steering is inlined into the installed persona, not loaded from a `resources` array. Claude
  Code uses a persona body verbatim as its system prompt and does not expand `@`-imports there, so
  `scripts/generate-personas.sh` appends every doc in the persona's steering domain (the same domain
  its kiro counterpart loads via `file://~/.kiro/steering/<domain>/**/*.md`), every doc in the
  `shared/` domain, and `security/env-file-protection.md`. The persona-to-domain mapping lives in
  `install/persona-domains.sh`. A new steering file in a domain is picked up on the next install,
  with no persona edit; edits to a persona source or steering doc take effect after re-running the
  installer. `scripts/validate-persona-steering.sh` checks the mapping and the generator output at
  commit time
- Personas have no kiro-style `knowledgeBase` equivalent. Where the kiro agent indexes local repos
  semantically (docs, ansible), the Claude persona instead documents the same local paths in a
  "Reference Repositories" table so Grep/Glob can be pointed at them manually — functional, not
  semantic, coverage
- Personas support their own scoped `hooks:` frontmatter field (`PreToolUse`/`PostToolUse`, same
  shape as the global `settings.json` arrays), confirmed against current Claude Code docs — but this
  repo doesn't use it. `block-persona-shell-commands.sh` (mirroring kiro's per-agent
  `toolsSettings.shell.deniedCommands` for aws/docker/kubectl/ssh/package-manager installs and
  persona-specific destructive commands) is wired ONCE as a global `PreToolUse(Bash)` hook in
  `settings.json` instead of duplicated into all four persona files. It self-scopes by reading the
  `agent_type` field Claude Code includes in the hook payload for any session run with
  `--agent <name>` — confirmed against current `hooks.md`, and empirically verified: a real
  `claude --agent docs` invocation produced a payload with `"agent_type":"docs"`, matching the
  persona's frontmatter `name:`. Main Claude Code sessions have no `agent_type` and the script
  no-ops for them

## Best Practices Followed

These practices come from the
[official permissions documentation](https://code.claude.com/docs/en/permissions) and
[hooks documentation](https://code.claude.com/docs/en/hooks):

- **Deny rules for sensitive files** — `.env*`, `.key`, `.pem`, `credentials*` all blocked via
  `Read` deny patterns
- **System path protection** — `/etc/`, `/usr/`, `/bin/`, `/sbin/`, `/System/` blocked for `Read`
  and `Edit`
- **Destructive command blocking** — `rm`, `sudo`, `kill`, `reboot`, mutating `gh` and `kubectl`
  commands denied
- **`git add .` blocked** — prevents accidental bulk staging
- **Hook-based enforcement** — `PreToolUse` hook provides defense-in-depth beyond permission rules
- **`async: true` on audit hook** — non-blocking logging that doesn't slow tool execution
- **`$schema` reference** — enables IDE autocomplete and validation for settings.json
- **Timeout on hooks** — 5s for blocking hook, 10s for async audit hook

## What Claude Code Does NOT Have (vs Kiro CLI)

- No equivalent to kiro's `code` agent as a *persona* — the main Claude Code session fills that role
  directly (the `docs`/`jira`/`datadog`/`ansible` personas do exist; see Personas above)
- No knowledge base integration (no semantic search over indexed repos). The `docs`/`ansible`
  personas document the same local KB paths in a Reference Repositories table for manual Grep/Glob
  instead (see Personas above). Kiro's `check-research-kb.sh`/`clear-research-kb-stale.sh`
  staleness-nudge hooks were deliberately NOT ported: the nudge tells the user to "ask me to
  re-index," but re-indexing requires kiro's `knowledge` tool, which Claude doesn't have — porting
  the nudge without a way to resolve it would just mislead the user
- No per-tool MCP audit hooks — see Hooks above for how shell-invoked `aws`/`kubectl` auditing works
  instead
- No `allowedTools` concept in the global permission model — see Permission Rules above
- No per-project working-file auto-load. Kiro's `code`/`docs`/`ansible` agents load
  `file://ideas.md` and `file://todo.md` relative to cwd, so the idea-refinement funnel's files land
  in context per-project. Claude Code has no equivalent glob/relative `resources` mechanism — its
  steering is global (`~/.claude/CLAUDE.md` + `rules/`), not per-project. The parity is carried by
  the `idea-refinement`/`todo` skills instead: they name the files and when to engage, so a Claude
  session reads them on demand rather than having them pre-loaded. Functional (skill-driven), not
  automatic (context-preloaded) coverage
- No auto-loaded README pointer map. Kiro loads the top-level `file://README.md` eagerly on all five
  agents as the always-on entry point, meant to be maintained as a thin doc *map* (the
  README-as-pointer scheme; see `etc/kiro-cli/README.md`'s Resource Patterns), and pulls the docs it
  points at on demand. Claude Code's only always-on context is the global `~/.claude/CLAUDE.md` plus
  (as of v2.1.277+) a project's own `AGENTS.md` — see the exception below. The parity for the
  README-pointer gap itself is carried by the `readme-pointer` skill: it names the convention (read
  the nearest `README.md` as a map, follow its one-hop pointers) so a Claude session does the same
  navigation on demand where no `AGENTS.md` exists.

**Exception, as of Claude Code v2.1.277+:** unlike the gaps above, Claude Code now *does* auto-load
one per-project file with no skill or steering needed — a repository's own `AGENTS.md`, read
directly as project instructions whenever no `CLAUDE.md`, `.claude/CLAUDE.md`, or `CLAUDE.local.md`
exists in the working directory or above it. A *user-scope* `~/.claude/CLAUDE.md` (what this repo
generates) does not count against that check, so the condition is met here: `AGENTS.md` auto-loads
in any Claude Code session started in this repo's checkout (`$AI_DOTFILES_DIR`; `~/.ai-dotfiles`
standalone). This repo deliberately keeps the default **Project instructions** setting
(`claude-md-or-agents-md`) rather than opting out, so a session here — or in any other personal repo
with an `AGENTS.md` and no `CLAUDE.md` — gets that file for free, matching the cross-tool parity
goal `AGENTS.md` itself states. This is also *why* this README absorbed the bulk of what used to
live in `AGENTS.md`'s "Claude Code Conventions" section: once `AGENTS.md` became live Claude context
on every session here, keeping Claude-only configuration mechanics there meant Claude re-reading
meta-documentation about its own plumbing every session for no coding-task benefit.

## Intentional Deviations

- **Steering generated by install script** — rather than manually maintaining `~/.claude/rules/`,
  `install/ai-tools.sh` generates per-file rules from shared `etc/ai/steering/` sources with
  `paths:` frontmatter for conditional loading. `CLAUDE.md` is a minimal pointer file.
- **No project-level settings** — only user-level `~/.claude/settings.json` exists. Official docs
  recommend `.claude/settings.json` committed to git for team sharing. Acceptable for personal use.
- **Built-in auto memory disabled (`autoMemoryEnabled: false`)** — Claude Code 2.1.x ships its own
  memory system that writes typed notes (`user`/`feedback`/`project`/`reference`) to
  `~/.claude/projects/<project>/memory/` on its own. This repo already has a more capable version of
  that: the `engram` MCP server plus the `correction-capture.sh` hook and the `distill-learnings`
  skill, which is cross-tool (shared with Kiro CLI) and promotes corrections to steering only after
  explicit user review. Running both would just create two uncoordinated memory systems writing
  about the same work.
- **Default `claude-md-or-agents-md` project-instructions setting kept** — see the `AGENTS.md`
  auto-load exception above.

## Finding Specific Information

- **What's allowed without prompting**: Check `permissions.allow` array in `settings.json`
- **What's blocked entirely**: Check `permissions.deny` array in `settings.json`
- **Hook scripts**: `etc/ai/hooks/block-env-files.sh` and `etc/ai/hooks/audit-shell-commands.sh`
- **Steering content**: Check `~/.claude/rules/`; source files in `etc/ai/steering/`
- **MCP servers**: Configured in `~/.claude.json` (bootstrapped by `install/claude-code.sh`)
- **Skills**: Symlinked from `etc/ai/skills/` to `~/.claude/skills/`
- **Personas**: `etc/claude-code/agents/*.md`, generated into `~/.claude/agents/` with steering
  inlined (`scripts/generate-personas.sh`)
