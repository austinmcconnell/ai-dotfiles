# Datadog Analysis Output

How to persist the output of a Datadog analysis so it survives the session and is useful to a future
agent (Datadog or code) checking a fix, hunting a regression, or building on prior work.

This is a **standing convention**, not a procedure. It applies to any non-trivial Datadog
investigation, regardless of whether an incident prompted it.

## Why This Convention Exists (read before deciding not to persist)

A Datadog analysis is **not** like a release analysis, and the difference drives everything below.

- A **release analysis** is a re-derivable cache over immutable inputs — git history. If the file is
  lost, it can be regenerated byte-for-similar from the tag range. That is why the
  `release-analysis` skill git-ignores its output without loss: the durable record is git itself
  (and GitHub Releases).
- A **Datadog analysis** captures **perishable observations**. Its inputs are not immutable and not
  fully re-derivable:
  - Full-resolution traces are retained ~15 days; rolled-up metrics ~15 months (site/plan
    dependent). An incident window from months ago may already be past trace retention — you are
    reading aged metric rollups, and some granularity is gone permanently.
  - Query results are point-in-time. Re-running the same query later can return different data as
    retention windows slide.
  - There is **no upstream system of record** for "here is what p95 looked like per version and
    which deploy moved the needle." Unlike release analyses, nothing else holds this.

Conclusion: "just re-run it later" does not work. The analysis is often the *only* durable capture
of data that no longer exists at that fidelity. That is precisely why it must be written down — a
stronger case for persistence than release analyses have, not a weaker one.

Do **not** blindly copy the release-analysis git-ignore rationale ("it's fine to lose, git has it").
That reasoning does not apply here.

## When to Persist

Persist when the analysis has durable value to a future reader. Concretely, persist if **any** of:

- The analysis reaches a **conclusion or recommendation** (e.g. "0.0.75 moved dashboard p95 from 90s
  to sub-second", "UST version tag missing on logs", "monitor X has no recovery threshold").
- It establishes a **baseline** a future agent may compare against to detect regression.
- It captures **perishable data** (metrics/traces/logs from a window approaching or past retention)
  that will not be re-derivable at the same fidelity later.
- It required **non-trivial query construction** worth reusing (the queries themselves are an
  artifact — see Provenance).
- It informs a **proactive** effort to find and fix issues before they escalate (this is a primary
  use case — not every analysis is an incident follow-up).

Do **not** persist ephemeral, low-value output: a one-off "is data flowing?" check, a
`pup auth status` confirmation, or a throwaway query with no conclusion. If in doubt and the
analysis took real effort or reached a finding, persist it.

## What to Persist

- The **question** the analysis set out to answer.
- The **findings**, quantified where possible (percentiles, counts, deltas — not "it got faster").
- The **conclusion / recommendation**, and what remains uncertain or unverified.
- Full **provenance** (see below) so the analysis is reproducible-in-intent and its freshness is
  auditable.

## Where to Persist

Default location:

```text
<project>/analysis/<domain>/<subject>-<YYYY-MM-DD>.md
```

For Datadog work in a project that uses this layout, that is:

```text
<project>/analysis/datadog/<subject>-<YYYY-MM-DD>.md
```

Guidance:

- Prefer `analysis/<domain>/` subfolders over a flat `analysis/` junk drawer, and over a top-level
  per-tool folder. A top-level folder (like `releases/`) is only warranted for a **homogeneous,
  unbounded, monotonic series** — same shape, one per event, indefinitely. Datadog analyses are
  **heterogeneous and episodic** (latency study, UST audit, cost/cardinality, coverage gaps), so
  they belong one level down under `analysis/`.
- If a project does not use `analysis/`, adapt the principle (`<investigations-dir>/<domain>/`)
  rather than forcing the exact path.
- **Git-ignore these files** — they are local working artifacts by default. Verify with
  `git check-ignore <path>` before writing if unsure.

## Local vs Shared Record

- These files are **local-only** by default. That is sufficient for personal investigation and
  cross-session continuity.
- If a finding needs to be **shared and durable** beyond the local machine, promote the *findings*
  to a real system of record — a post-mortem doc for incident follow-ups, or a Jira ticket for
  tracked work. Do **not** rely on a git-ignored file to be that shared record.
- The file is the working capture; promotion to a system of record is a separate, deliberate step.

## Provenance (mandatory)

A latency number with no query and no date is nearly worthless months later. The same number with
its query, window, and caveats is durable evidence. Every persisted analysis MUST record:

- **Capture timestamp** — when the analysis was run (date, ideally time + tz).
- **Datadog site** — `ddog-gov.com` (this org uses GovCloud).
- **Exact queries** — the `pup` commands / metric queries / log queries run, verbatim, so a future
  agent can re-run or adapt them.
- **Time window(s)** queried — absolute dates, not "last 7 days" (which drifts).
- **Retention caveats** — which data came from full-resolution traces vs aged metric rollups, and
  whether any part of the window is past retention (granularity lost).
- **Tag-availability caveats** — e.g. clean per-`version` splits depend on `DD_VERSION` being wired;
  note the earliest version/date for which a given tag split is reliable, and how you attributed
  data before that (e.g. deploy-timestamp correlation).
- **What was NOT verifiable** — gaps, missing tags, absent data, assumptions made.

## Relationship to Other Conventions

- **`development/release-analysis` skill** — a deliberately *contrasting* pattern. Its output is
  re-derivable from git, so its git-ignore reasoning is "safe to lose." Do not transfer that
  reasoning to Datadog analyses (see "Why This Convention Exists").
- **`memory-management` skill / engram** — the *convention* lives here in steering (loaded every
  session). A specific analysis's *findings* may additionally be saved to engram when cross-session
  recall is useful. Steering answers "how do I persist a Datadog analysis"; engram answers "what did
  the last one find."
